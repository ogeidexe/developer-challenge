# ADR-012 — 403 vs 404 for Resources Outside Visibility

**Status:** Accepted (mandated by README §5.5: "Decida entre 403 e 404 nesse caso e justifique em ADR") · reviewed 2026-11-18 against the implementation
**Date:** 2026-11-15

## Context
README §3.2: `404` for nonexistent resources "ou fora da visibilidade do usuário. Decida entre 403 e 404
nesse caso e justifique em ADR". Drafts are visible only to their owner (§2.2), and the list is scoped
per role — so id-probing could otherwise reveal existence.

## Problem
Pick one consistent stance for "exists but you may not see it".

## Options Considered
1. **404 everywhere** for invisible resources (existence not disclosed).
2. **403 everywhere** with a generic body (simpler mental model, leaks existence via status).
3. **Split by operation:** 404 for resource access (GET and aggregate loading), 403 for action-type
   authorization failures (role cannot perform this kind of action at all).

## Decision
Option 3, implemented uniformly:
- Loading any request (GET one, transitions, versions, history) applies the visibility predicate; failure → **404 `NOT_FOUND`** (BR-14 stage 2).
- **Drafts are owner-only — `ADMIN` included.** README §2.2 ("Rascunhos (DRAFT) só são visíveis para o dono") is the explicit, specific rule and overrides §1.1's general "ADMIN vê tudo". Consequence (A-26): `ADMIN` can cancel any *visible* request — `PENDING_APPROVAL`/`CHANGES_REQUESTED`; a foreign DRAFT is invisible to ADMIN (404 at load), so in practice DRAFT cancel is owner-only. This is the only reading that keeps §2.2 and §4.2 ("dono ou ADMIN") simultaneously true.
- If the resource loads but the caller's **role** cannot perform the action type (e.g. `SOLICITANTE` calling approve, non-ADMIN calling `POST /users`) → **403 `FORBIDDEN`** (stage 3, before lock/business checks).
- If the action is **owner-only** and the caller is not the owner (edit, submit, or cancel by a non-owner non-ADMIN) → **403 `NOT_REQUEST_OWNER`** (A-27) — distinct code so the front-end can distinguish "wrong role" from "not your resource". Evaluated after visibility, before the lock check.
- Business-level authorization failures (not eligible for the step, segregation) are **422 domain codes**, not 403 — the role type was allowed but this instance is not (README's own examples: SELF_APPROVAL_FORBIDDEN, APPROVER_NOT_ELIGIBLE are 422).

## Rationale
Uniform 404 prevents oracle leaks (a competitor cost center cannot enumerate request ids nor discover
draft existence — directly satisfying §2.2's "rascunhos só visíveis para o dono"). 403 for action types
preserves a meaningful signal for the front-end ("your role can't do this" → hide affordances) without
leaking data. This matches README §4.3's ordering (existence/visibility → 404 before role → 403).

## Consequences
- Front-end treats 404 on detail as "not found / not visible" screen; 403 `FORBIDDEN` as role messaging
  (hide the whole action family); 403 `NOT_REQUEST_OWNER` as "not your request" (hide owner-only
  affordances); 422 banners carry the explanatory `detail`.
- Tests: `AccessPolicyTest` (visibility matrix, drafts invisible to ADMIN), `WorkflowIntegrationTest.draftsAreInvisibleEvenToAdmin`,
  `SecurityIntegrationTest#anApproverOfAnotherCostCenterSeesNothingAndCannotDecide` and
  `#anotherRequesterCannotReadEditSubmitOrCancelSomeoneElsesRequest`, the Cypress spec `08-navigation` (404 page
  for another user's draft and for another center's request) and the checklist items LIST-04, LIST-05 and
  FLOW-05 (a 404 wins over role, version and comment errors), in both suites.
- Implementation: `domain/AccessPolicy.canSee`, `application/RequestAccess` (load → 404; role/owner → 403).

## Trade-offs
Slightly less debuggability for legitimate users (a real typo'd id and a foreign id look alike) —
acceptable for an internal tool with an audit focus.
